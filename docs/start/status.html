On this page

Status and results ​

Octryx AI is the layer above your coding agent: you bring Claude Code or Codex, Octryx AI brings the process, the checks and the record. This page says what works today, what we measured, and what comes next. Every feature carries one of four stages, always in this order:

Planned→Building→Built→In real runs
StageMeans
PlannedDecided, not started.
BuildingBeing built now; not usable yet.
BuiltBuilt and verified locally; not yet proven in real runs.
In real runsUsed end to end in real workflow runs, with results.

The bars in each label fill up from one to four as a feature moves along.

How a run works ​

  1. A work item comes in: a bug or a story from your tracker, or a line in the chat.
  2. A workflow takes it: for a bug "Bug fix with a reproduction test", for a story "Story / epic delivery". The workflow fixes the phases, the checks and who has to approve what.
  3. Your coding agent does the work on your machine: Claude Code or Codex runs on your own subscription or on company models, in a clone of the repository; without a device, on a server runner. Octryx AI starts it phase by phase.
  4. The platform checks, not the agent: for a bug, the new test must fail before the fix and pass after it. The repository's declared tests run without the agent. An independent review reads the change.
  5. You get a pull request and a record: phases, evidence, tokens and cost of the run, next to the pull request.

Results ​

In real runs Measured on one machine, with Claude Code on a Claude subscription.

Acceptance run on a freshly rebuilt stack ​

We rebuilt the whole local stack from scratch and ran six cases at the same time: one bug and one story each in Flutter, Python and Node. 6 of 6 completed without a human, for $1.01 in total.

Time to the first pull request ​

The first start takes about 5 minutes plus the image download. After that: 2:57 min from the stack's start to the review bot's comment, measured once on 0.0.1-alpha, on a freshly started development stack on a Mac with the images already built, with a Claude subscription (Sonnet 5 writes the fix, Sonnet 5.5 runs both reviews), no human step, no refused action, no loop. starting the stack with the demo 48 s; sign-in, install and device about 30 s; from Start to the pull request 69 s (preparation 3 s, fix with its first passing test 48 s, pipeline including the proof “red on the old code” 2 s, independent review 19 s, passed with no findings); the bot's review 23 s after the pull request. One measured cold run on one Mac; numbers vary with the machine and the model.

Compared with plain Claude Code ​

How we measure, and how to do it yourself: Set up a benchmark workspace.

The same cases, once through Octryx AI and once with Claude Code alone:

  • Python and Node: 0.6 to 1.6 times the time of plain Claude Code, at 0.2 to 0.5 times the cost.
  • Flutter story: 2.6 to 3.0 times the time on the first run; 0.7 times on a repeat run.

Honest limits ​

  • Flutter is still several times slower than plain Claude Code on a first run. Most of the time goes into the build and the browser test.
  • All numbers come from one machine. They are not a benchmark across teams or hardware.

Now ​

Pull request review bot ​

Built Octryx AI reviews pull requests in your repositories, including the ones its own runs open. Details: Pull request review bot. Its scanners (gitleaks for secrets, osv-scanner for vulnerable dependencies) run on a review seat's device; a committed secret fails the status. Built
  • It picks up a pull request the platform opens within about 5 seconds; the bot's review came 23 seconds after the pull request in the measured demo run.
  • GitHub and Bitbucket are built. GitLab is In real runs on a self-hosted instance: summary and inline findings, the commands explain, pause, resume and ignore, an incremental pass after a fix push, and the webhook. review full, fix and write tests are built but not yet run on GitLab.
  • The review status informs by default: findings are reported and the status stays green. A team can switch a repository to "Required check", so blocking findings fail the status.
  • Corrections feed back: ignore with a reason proposes a team rule; answers to findings are counted as corrections.

Secrets stay out ​

Built Secret redaction covers prefixed names, JSON and YAML, quoted values, URLs and known token forms. Job output and transcripts are redacted on the machine before they are sent; see Secret redaction.

Nothing installed system-wide ​

Built The launcher brings its own pinned tools (ast-grep, Playwright, Chromium, gitleaks). Nothing is installed system-wide.

From correction to check ​

When a person corrects an agent, that correction should become a check, so the same mistake is caught next time.

  • Built Corrections are captured and counted.
  • Building A proposed check needs a four-eyes approval on its own screen; the screen and its rules are built and shown with sample data so far.
  • Building Proposing a check and proving it automatically.

Fair browser tests ​

Built A browser scenario that cannot work on an app is detected and never counted as a failure of the agent.
