Set up a benchmark workspace ​

In real runs How we measure Octryx AI against a coding agent on its own, every setting we use, and how to run it yourself. The results are on Status and results.

The workspace ​

SettingValue
Workspace"Octryx Bench", on a local stack on one Mac
Data classInternal

An app that declares no system test counts that criterion as "n/a", listed separately.

The cases ​

  • Three apps in one repository: a Flutter web app (a coffee-brewing app), a small Python app and a small Node app.
  • Each case pins a base branch and a base commit. A case is refused when the branch has moved, so it cannot change silently.
  • Nightly set: 6 cases, one bug (S) and one small story (M) per stack.
  • On-demand set: 11 more Flutter cases, taken from real runs and approved by a person.
  • Each case has a fixed clone folder on the device, on the device's folder allow list.

The benchmark repository ​

The cases are public at github.com/octryx-ai/octryx-bench:

  • the three apps on main;
  • each case's base as its own branch or tag;
  • a copy of the case briefs, the same text the runs start from (some are in German, as they were written).

Each base branch is one commit, and cases/cases.json in the repository names the same commit per case. Check out a base before you run its case; the commit must match, or the result is not comparable.

A round ​

The suite runs nightly, after the merge gate, or on demand, one case after another or all at once. For each case it:

  1. resets the clone to its base (leftovers are stashed, never deleted);
  2. creates a new work item through the API;
  3. starts the run on the device and watches it, with no human step;
  4. at the end, stops a run that is still open and closes its pull request; the branch stays.

What is measured ​

Outcome per case

  • completed: done, or a pull request is open;
  • paused: paused or waiting for a person for more than 3 minutes, with the cause: platform, agent, environment or person;
  • failed: stopped, failed, or over the 45-minute limit.

Time and cost come from the run's events: wall time, and cost at list price for seat use, with real API cost reported separately. They are also exported as Prometheus metrics.

A rubric (version 2) checks yes-or-no criteria from the events and the pull request:

  • proven: a story counts only with a green last pipeline, nothing unproven, and a new or changed test in the pull request;
  • system test green;
  • review passed;
  • pull request opened;
  • no intervention.

Each round, people check 2 sampled cases by hand, and the report shows how often they agree with the rubric.

Compared with plain Claude Code ​

The same bug and the same story go to plain claude -p with the same model, base commit, brief and machine. Reference figures: the bug in 73 s for $0.26, the story in 208 s for $0.33. The report shows the factor Octryx AI ÷ plain.

Plain runs vary a lot: the same story took between 9.5 and 23 minutes within one hour. Compare against a plain control started at the same time, not only against fixed numbers.

Run a round yourself ​

The harness that runs the rounds is in the product repository, under scripts/e2e. The cases are in scripts/e2e/cases.json.

You need

  1. A running stack: see Docker Compose. The demo data is not needed.
  2. In the Workspace, the workflows Bug fix with a reproduction test and Story / epic delivery, and the seat models admitted.
  3. A device registered with the stack and running octryx-claude, with Claude Code signed in to a Claude subscription (Launcher and devices). The cases use the seat and Sonnet 5.5.
  4. One clone folder per case, <cases_dir>/e2e-<case id> (default ~/bench-cases), with a clone of octryx-bench and the case's base branch base/<case id>-env checked out. Every folder must be on the device's folder allow list.
  5. An admin API key for the stack, in a file: ~/.octryx-e2e/api-key, or the path in OCTRYX_E2E_KEY_FILE. The key is never written anywhere.

Your installation's values go into scripts/e2e/cases.local.json, which Git ignores. cases.json ships with the placeholders <workspace-id> and <device-id>; the local file sets defaults (api, project_id, device_id, cases_dir, stack_checkout), can change single cases under cases, and has an env block. A setting is taken from the environment first, then from that env block, then from the default. The README in scripts/e2e has an example under "Your installation".

SettingDefault
OCTRYX_E2E_KEY_FILE~/.octryx-e2e/api-key

Run it from the root of the product repository:

sh
python3 -m scripts.e2e.nightly --dry-run                         # checks cases, folders and bases, starts nothing
python3 -m scripts.e2e.nightly                                   # the 6 nightly cases
python3 -m scripts.e2e.nightly --schedule on-demand              # the 11 on-demand cases
python3 -m scripts.e2e.nightly --schedule all --all-parallel     # all 17 at once
python3 -m scripts.e2e.nightly --cases flutter-bug               # one case by its id

Without --all-parallel, the cases of one stack run one after another, and two stacks run at the same time. For a daily round we use scripts/e2e/nightly-e2e.sh, a scheduler for a Mac (screen session, 03:30). A case whose branch has moved off its base commit, or whose folder is not on the allow list, is not run, and the report says why.

The report lands in the report folder:

  • latest.md and <date>.md: the outcome per case (completed, paused, failed), wall time and cost, and the rubric criteria;
  • <date>.json: the source for the trend across rounds;
  • e2e.prom: the same figures as Prometheus metrics;
  • <date>.audit.json and review/index.html: the 2 sampled cases for the check by hand, with a read-only page to go through them;
  • summary.txt: a short summary of the round.

python3 -m scripts.e2e.rescore e2e-reports/<date>.json scores a finished round again with the current rubric.

Do it yourself ​

The same method on your own repository:

  1. Pin a base commit.
  2. Write one bug with a clear reproduction and one small story with at most three acceptance criteria.
  3. Start plain claude -p with the same brief and a run in Octryx AI at the same moment, on the same machine and model.
  4. Compare wall time, cost, and whether the result is proven by tests: a test red on the old code and green with the fix, and the declared tests green.

Run each case more than once: a single run says little.
