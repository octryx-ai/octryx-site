Work items and intake ​

In real runs Work items are the bugs, stories, epics and tasks of a Workspace, from intake to done. Runs start from them.

The Work area ​

GroupPages
PlanWork items, Plans
DeliverRuns, Epics, Coding sessions, Repositories
ConfigureCoding rules, Intake

Every Workspace member can read work items, plans, runs and epics. Starting a workflow, moving or closing items and the Configure pages need an operating role.

Work items ​

Board or Table, and My work or All items. A work item, and an intake, stay in the Workspace they were created in: a change of Workspace is refused (workspace_immutable). For My work, you choose once per Workspace who you are in Jira (Who are you in Jira?); Octryx AI never guesses it from your email or name.

  • Filters: Search work…, Jira status, Assignee, and under More filters source, project, work state, sync, automation, labels, fix version and sprint. Clear resets them.
  • The board has one column per state: Intake, Clarification, Ready for plan, Planning, Plan review, Ready for development, Development, Validation, Review, Changes requested, Ready to merge, Done, Blocked, Rejected. An unknown state gets its own column, so nothing is hidden.
  • Badges show only exceptions, such as Blocked or Agent may start.

Start a workflow ​

Open an item and choose Start workflow: the Workflow, the Run on target (a device or the server) and the Model, then Start run. If no workflow fits, the form says: "No workflow can start for this item yet. Publish one in Agents › Workflows."

Under Advanced:

  • Repository and Branch to review (for Review & PR workflows);
  • Rounds per loop;
  • Cost budget (USD): the run pauses when its model cost reaches this amount.

Save run limits keeps both limits on the item; an epic or story can pass them to all its children. You can also start a workflow from the chat, for example "Fix OCX-1".

The item's detail has Overview and Activity: the change plan, analysis, repository impact, pull requests, linked issues, the audit timeline and how its state was mapped from the source.

Intake ​

Work › Intake decides which tickets come in. Sources: Jira, ServiceNow and your own REST API. The setup has five steps: Source, What, When, How, Preview.

  • When: Manual only, every 15 minutes (the default), hourly, every 4 hours, daily at 06:00 (Workspace time zone), or a custom schedule.
  • When an item arrives: Suggest only (the default), Agent may start (only items with the Workspace's automation label), or Humans only.

Statuses are mapped in this order: your configured mapping, a built-in list (for example done, in progress, in review, blocked), the source's status category, and otherwise Intake, which the sync summary reports as unmapped.

Writing back to Jira ​

Built Write-back is off until a Workspace admin switches it on, under Admin › Connections › Jira write-back. Create the standard write-back (dry-run) creates a table of Octryx AI states, Jira transitions and what else is written. It starts in dry-run: it shows what it would write. Switch to execute… and Activate… turn it on, each with a confirmation.

Plans, epics and pull requests ​

  • Plans: All plans and Waiting for review. Who approves a plan is set in Admin › Rules › Approval rule.
  • Epics: an epic's stories with their tasks, pull request and cost; states such as Needs you, Building, Shipped or Failed.
  • Pull requests: a run records the pull request it opens, and the item's detail lists it. While the run waits for the merge or decline, it refreshes that pull request. There is no separate pull request page and no manual sync or refresh yet Planned.
