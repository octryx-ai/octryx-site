Architecture ​

How the parts of Octryx AI fit together: what runs on the server, what runs on a developer's machine, where agents run, and how a request moves through the platform.

Since 0.0.2 no agent runs inside the platform. Every agent turn runs as Claude Code or Codex, either on a developer's device or on a server runner. The platform keeps the sessions, the rules, the checks and every model call.

The parts ​

PartRuns whereWhat it does
Platform (api)your server, in Docker Compose or KubernetesThe web app, the REST API, the MCP server for coding clients, sessions, workflows and their checks, Knowledge, the review bot, connections, audit, and the gateway every model call goes through
LiteLLMnext to the platform, on the api pod's loopback onlyThe models: the platform reaches them through LiteLLM. Bundled with the platform, or an external LiteLLM gateway. See Models
PostgreSQLnext to the platformAll records, the Knowledge search index, and LiteLLM's own database
Object storenext to the platform (bundled in Compose) or your S3-compatible storeThe originals of Knowledge sources, uploads and evidence. See Knowledge storage
migrate, secrets-initonce at each startBring the database to the current version and set up the bundled LiteLLM's database; create the keys on the first start (Compose). See Upgrade
Runner gatewaynext to the platformThe server runners' only way to the platform: it forwards the api's port and nothing else
Server runners (runner)your server, sandboxed containers from the octryx-runner imageRun Codex turns for people who do not use their own device. See Server runners
Launcher octryx-claudeeach developer's machine, and inside every server runnerStarts Claude Code or Codex under the Workspace's rules, and as a device takes chat turns and the run phases that change and test code. See Launcher and devices
Your toolswhere they areJira, Confluence, GitHub, GitLab, Bitbucket and others, reached through connections

The platform never builds or tests code itself. That happens on a device or a server runner, in a clone of the repository, with Claude Code or Codex. Pushing, opening pull requests, updating tickets and the review happen on the platform, so neither a developer's machine nor a runner holds a Git host or Jira credential. See Network and Git and Egress allowlist.

Where an agent turn runs ​

WhereEngineModels
A developer's deviceClaude Code or Codex, whichever the device reported to the platformThe Workspace's governed models through the platform's gateway, or the person's own Claude or ChatGPT seat through the platform's seat relay
A server runnerCodexGoverned models only, through the platform's gateway; never a person's seat

Chat turns from the web, the phone, /api/v1 and Teams, scheduled tasks, and the turns of a workflow run the server runs go to the server runners unless they run on a person's device. A Workspace can forbid server runners.

A server runner:

  • enrolls with the installation's join secret, and the platform sees it as a device of a technical account;
  • runs Codex under a separate agent account with no capabilities, on a network that reaches only the runner gateway: no database, no LiteLLM, no Git host, no internet;
  • serves one person in one Workspace at a time, and empties its disk before it switches to another;
  • runs on the container runtime the installation configured (for example gVisor); the platform admits only runners on that runtime.

To add tools to the runner image, see Extend the runner image.

Sessions live on the platform ​

After each turn the launcher uploads the engine's session files (Claude Code's transcript, Codex's thread). The platform keeps them encrypted, and only the device that runs the session's active turn can fetch them. So a thread survives its runner container and moves to another device, another runner or another person:

  • A person can hand a session to a colleague or put it into the Workspace's pool. See Session pool.
  • A run phase on the server runners that needs a person's Claude or ChatGPT seat pauses until that person takes it over on a device that holds the seat. See Seat takeover.

A run, end to end ​

  1. A work item comes in, from Jira, the web app, the phone, Teams or the chat.
  2. A workflow is started on it. The platform decides the phases and their checks.
  3. For a phase that changes code, the platform hands a job to a device or a server runner. The launcher starts Claude Code or Codex there, in a clone of the repository, with a phase brief. With every server runner busy, the turn waits for one, first come first served.
  4. A server runner gets the run's branch from the platform over read-only git, with a short-lived token bound to the run. It cannot push.
  5. Every tool call passes the launcher's check first; every model call passes the platform's gateway with its policy, budget and content handling. Governed calls go on to LiteLLM; seat calls go to the person's own subscription.
  6. After the phase the platform runs its own checks: the declared tests without the agent, the proof that a new test fails on the old code, an independent review. A failed check goes back to the agent a limited number of times (a Workspace setting, 3 by default); then the run pauses, so red work is never reported as done. See Evidence and checks.
  7. The platform pushes the branch, opens the pull request and reports back to the ticket. The review bot reviews the pull request.
  8. Everything lands in the run's record: phases, evidence, tokens and cost. See Runs and their record.

Inside the platform ​

The backend is one Python application (backend/app in the repository):

AreaOwns
api/routes, web/routersHTTP: /api/v1 is the API (including the device channel, the agent gateway and the model gateway routes); the web app also uses its own /chat/api routes
servicesBusiness logic, policies and orchestration
services/sessionA turn: preparation, the execution gate, the hand-over to a device or runner, completion; session handovers and the pool
services/devicesDevices and server runners: the device channel, jobs, the runner pool and its queue, the engine session files
services/agent_gatewayClaude Code and Codex started by the launcher: identity, sessions, tool decisions, seats, the run-bound git token and the read-only git a runner fetches the run's branch from
services/model_gatewayAdmission, policy, data class, cost and audit of every model call; the coding agents' model routes; the bundled LiteLLM
services/workflow_runsWorkflow runs: their phases, checks and platform actions
agent/providersThe client of the LiteLLM gateway
agent/runtimeThe model-call mechanics the platform keeps for its own model calls: fallback, provider errors, admission, usage and prompt templates
toolsTool definitions, registry, visibility and dispatch, with each tool's risk and approval metadata; deny by default

A turn goes: route → session preparation → the turn's execution profile → the execution gate, which hands no turn on for a profile that is not allowed (and holds a turn that names a workflow until the person confirms it) → a job for a device or a server runner → the launcher starts Claude Code or Codex → model calls through the model gateway, tool calls through the session's MCP endpoint, where the registry, the visibility rules and the tool access policy decide what may run.

The session's MCP endpoint lists a small basic set plus tool_search and tool_call. A write or admin tool called over MCP waits for a person's approval in Octryx.

The web app is a React application in frontend/chat. Its look and its rules are in the design guide.
