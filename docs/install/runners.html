Server runners ​

Built Server runners are a pool of sandboxed containers your installation runs itself. A chat turn, a scheduled task or a workflow step that does not run on a person's own device runs on a server runner, as Codex, under the same launcher, driver and hooks as on a device. The platform sees each runner as a device of the technical account octryx-runner, serving every Workspace that allows server runners.

What a runner is ​

  • One image: octryx-runner, with Codex pinned, the launcher, Python, git, ripgrep, ast-grep, ruff and a headless Chromium with Playwright. No language toolchains: add yours in your own image.
  • Two accounts: the launcher (uid 10001) holds the device credential and writes each session's Codex configuration and hook chain. Codex and everything it runs (commands, tools, hooks) run as the agent's account (uid 10002), with no capabilities.
  • Read-only where it matters: the session's configuration, its hook chain, the launcher and Codex itself are read-only for the agent, so even a session with full access cannot switch its hooks off. The launcher checks the chain between rounds.
  • A token broker: the agent's processes get the model-gateway and MCP tokens they need from a socket of the launcher, never the device credential or the join secret.
  • Governed only: a runner runs models through the platform's gateway, never a person's seat. A phase that needs a seat pauses for a seat takeover.

Behind the container boundary Codex runs without its own sandbox. "Ask before changes" in the chat becomes Codex's approval policy untrusted: every command not known to be read-only is asked in the chat.

Network ​

A runner reaches only the runner gateway, a small nginx that forwards to the platform's port. No database, no object store, no LiteLLM, no internet, and no git host: git push has nowhere to go.

A gateway call from a runner acts for the person whose turn it runs, and only while that turn is active: their Workspace membership, budget and usage, never a standing access of the runner account.

One person at a time ​

All sessions of a runner share the agent's account and its disk. So a runner serves one person in one Workspace at a time: the platform offers it nobody else's turn while one is active. Before the first turn of another person or Workspace, the launcher empties the working folders, the agent's home and the Codex and session state.

A thread that comes back to an emptied runner gets an empty folder; the launcher restores its Codex thread from the session files the platform keeps. The platform prefers the runner that already holds the thread when it is free, else the least busy one.

Repositories on a runner ​

A runner holds no credential of the Workspace's Git connection. It reads the run's branch from the platform:

  1. It asks for a run-bound token, valid 10 minutes and checked again on every request: the turn must still be active, the person still a member, and the session and the run still bound together.
  2. It fetches over read-only git from the run's working copy on the platform. Only the run's branch is visible. The token is never written to a URL, the command line or .git/config, and the agent's account never sees it.

Nothing is pushed from a runner. The change goes to the platform as a patch; the platform pushes the reviewed change with its connection and opens the pull request. See Git repositories and pull requests.

When every runner is busy ​

A chat message is kept and its turn waits as Waiting for a server runner until one is free, first come, first served. Stop cancels the wait. Without any server runner set up, the message is refused as needs_configuration (runner_pool_not_set_up).

Docker Compose ​

docker compose up -d starts one runner next to the platform (service runner). More with:

bash
docker compose up -d --scale runner=3

Nothing else is needed: the first start writes a join secret into the runner_join volume, which only the platform and the runners mount, and each runner enrolls with it. A runner keeps its device credential in memory, so a restarted container enrolls as a new device; the old one stays offline in Admin › Devices until you remove it there.

The runner container has a memory limit of 4 GB.

Kubernetes ​

The chart's runners are off by default.

ValueWhat it does
runners.enabledtrue runs the runners and the runner gateway
runners.replicashow many runner pods (default 1)
runners.runtimeClassNamethe RuntimeClass of the runner pods, for example gVisor; empty: the cluster's default
runners.storagesizes of the runner's tmp, workspace and state (default 2Gi, 4Gi, 1Gi)
runners.networkPolicy.enableddefault true: a runner's egress is the runner gateway and the cluster DNS, and nothing reaches a runner (runners.networkPolicy.dns says where DNS runs)
resources.runner, resources.runnerGatewayrequests and limits (runner default: 500m / 1Gi, limit 2 CPU / 4Gi)
images.runner.repository, tag, digestyour runner image

Also:

  • Build and push the runner image: docker build -f docker/runner/Dockerfile -t <registry>/octryx-runner:<tag> ., then set images.runner.repository and tag.
  • Add RUNNER_JOIN_SECRET (any long random value) to the existing Secret. The platform reads it; each runner pod gets only that key, as a file.
  • Your CNI must enforce NetworkPolicy. Check that it does.
  • The runner container starts as root with only the capabilities CHOWN, FOWNER, FSETID, SETUID and SETGID, used to hand its writable places to the launcher and the agent's account. The namespace needs the Pod Security level baseline, not restricted.
  • A new pod enrolls as a new device.

Container runtime: gVisor ​

Codex runs code with a shell, so the hardened option is gVisor (runsc), a user-space kernel between the session and the host. The runtime is configured, never guessed:

  • Compose: RUNNER_RUNTIME=runsc in .env. Docker then refuses to start a runner on a host without that runtime.
  • Helm: runners.runtimeClassName, for example gvisor. Kubernetes starts no runner pod whose RuntimeClass does not exist (kubectl get runtimeclass).
  • In both, the platform admits only runners that report that runtime when they enroll (runner_runtime_mismatch). With no runner admitted, a turn for the pool answers needs_configuration (runner_pool_unavailable). Nothing falls back to the default runtime.

Installing gVisor is the host's or the cluster's part: see the gVisor installation guide.

Not run end to end yet

gVisor is configured and enforced as above, but a chat turn and a workflow run on gVisor itself have not been run end to end yet.

Switch runners off for a Workspace ​

A Workspace forbids server runners with server_runners: "forbidden" in its configuration. Then neither a chat turn nor a workflow run of that Workspace lands on a runner.

A browser in the session ​

A run phase that asks for a browser gets the same Playwright MCP server as on a device, with Chromium for this session only: headless, its own profile, loopback pages only. A runner has no internet, so the image carries both at pinned versions. The session starts its app on 127.0.0.1, opens it and sees the screenshots.

Size ​

The image is about 5 GB: Python's Playwright and the Playwright MCP server each bring their own Chromium.

Limits ​

  • gVisor is not run end to end yet (see above).
  • A restarted runner enrolls as a new device; remove the old one in Admin › Devices.
  • A runner serves one person in one Workspace at a time; more parallel work needs more runners.

See also Known limitations.
