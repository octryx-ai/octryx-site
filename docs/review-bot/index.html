Pull request review bot ​

Built on GitHub and Bitbucket · In real runs on a self-hosted GitLab, webhook and sync

Octryx AI reviews the pull requests in your repositories, including the ones its own runs open. It posts one summary comment, inline findings with a severity, file and line, and a commit status. It never approves, never merges, and pushes only when someone asks it for a fix.

What a review looks like ​

One summary comment per pull request, edited in place on every pass:

  • the verdict, looks good or changes requested, and a one-sentence summary;
  • Findings: counted as 🔴 high, 🟠 medium and 🔵 low, with how many sit inline;
  • findings outside the changed lines, as a table;
  • the story's acceptance criteria as a table, for information;
  • findings still open from earlier passes;
  • Look closely here: the hotspots of the change;
  • a size note for a large pull request (it never blocks);
  • a folded Walkthrough that says, file by file, what to read carefully (🔎), what to skim (👀) and what is mechanical (⚙️);
  • a footer with the reviewed commit, the ticket, the reviewer model and the Octryx AI run.

Inline comments, one per finding: severity, a number (F1, F2 …) and the fix. Where the host supports it, the fix is a one-click suggestion: a suggestion block on GitHub and GitLab, a plain "Suggested change" code block on Bitbucket. Before posting, the bot checks the suggestion's line range, so it covers the lines it really rewrites. For Python it also applies the suggestion to the file: if the result does not parse or uses an undefined name, the suggestion comes as text to apply by hand, not as one click.

A commit status that informs by default or gates the merge if you want it to. See Settings per repository.

How it works ​

  1. A pull request opens or changes. The bot hears it through the host's webhook, through its hourly sync, or both. A pull request that an Octryx AI run opens or pushes to is picked up within about 5 seconds; in the measured demo run, the bot's review came 23 seconds after the pull request opened.
  2. An independent reviewer reads it. A fresh session without the author's history reads the change, the linked ticket and the spec. A deterministic check adds callers that the change breaks outside the diff, and a failed CI check becomes a finding too.
  3. The bot posts the summary, the inline findings and the status.
  4. People answer in the thread. @octryx explain, ignore, pause, resume, review full, and fix when fix runs are on and the PR fix workflow is switched on. See Commands.
  5. A fix is pushed. The next pass reviews only what changed since the last one: a fixed finding gets "✅ Fixed in abc1234" and its thread is resolved; a partly fixed one gets "◐ Partly fixed in abc1234" and stays open with only the rest. The summary counts fixed, still open and new.
  6. People push back. When a person answers a finding in its thread, the next pass weighs the answer: without new evidence for the finding, it is withdrawn ("↩️ Withdrawn after the answer in this thread"), the thread is resolved and the summary lists it. The answer is also kept as a counted correction, and @octryx ignore proposes a team rule. See Learning from corrections.

Scanners ​

Built Next to the reviewer, pinned static scanners (gitleaks and osv-scanner) check the changed files. They run as one job on the device of a review seat (the team's first, then the author's), never on the server, and they never run the pull request's code.
ScannerFindsRuns
gitleakscommitted secrets: always high, the value is never quoted, and the status failsalways
osv-scannerknown vulnerabilities in dependenciesonly when a manifest or lock file changes
  • A linter's finding counts only on lines the pull request changed, and never above medium.
  • At most 30 scanner findings per review; the footer counts the rest.
  • A scanner that is missing, failed or timed out is named in the footer, and the review goes on without it. So does a review with no seat device to run the scan.
  • The scanner list is data (stacks.json, general.scanners; a stack can add its own).
Planned A code-pattern scan (SAST) with Octryx AI's own Apache-2.0 rules, after the alpha.

Where the review runs ​

The review uses a person's own subscription where it can, and the company's model route only as a visible fallback:

  1. The review is offered to every member of the Workspace whose review seat is on, except the author. The first device that accepts runs it.
  2. If nobody accepts within 90 seconds, the pull request author's seat is asked.
  3. Otherwise the company route with the same model takes it. This is recorded as a visible event and counts against the run's budget.

A seat review is a single call on the person's machine: no tools, no MCP servers, an empty temporary folder, and a time-out after 300 seconds. The server never holds the subscription. A seat review costs nothing extra; its list-price equivalent is still recorded, separately from real API cost.

The review seat is on by default for Workspace admins and owners and off for everyone else.
