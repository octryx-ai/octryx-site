Commands in a pull request ​

Built · In real runs on a self-hosted GitLab for explain, ignore, pause and resume, over webhook and sync; review full, fix and write tests are built

Write a command in a pull request comment, on its own line, starting with @octryx. The bot answers in the same thread.

CommandWhereWhat it does
@octryx explain [question]in a finding's thread, or anywhereExplains that finding, or answers the question about the change, in at most 12 lines. Read-only.
@octryx ignore [reason]in a finding's threadRemoves the finding, replies "🙈 Ignored by …", resolves the thread and proposes a team rule.
@octryx pauseanywhereStops reviews on this pull request, from webhook and sync.
@octryx resumeanywhereStarts them again.
@octryx review fullanywhereA full review of the current commit, even if it was reviewed before and even while paused.
@octryx fix [note]in a finding's thread, or anywhereA fix run: the one finding, or all open blocking findings. Needs fix runs switched on and the PR fix workflow on (see below).
@octryx write tests [note]anywhereA fix run that may change only test files.

Anything else after @octryx gets the help text as an answer. Each comment is acted on once, and only on open pull requests.

Who may use them ​

The commenter's host account must be linked to an Octryx AI user (My settings › Profile, card Linked accounts) who has a role in the Workspace. On top of that:

  • GitHub: write, maintain or admin permission on the repository;
  • GitLab: Developer or higher;
  • Bitbucket: the bot cannot read repository permissions there, so a Workspace admin or owner.

Anyone else gets one polite refusal.

ignore ​

ignore works only in a finding's thread. Later passes no longer report a finding in the same file within three lines. A reason is optional but worth giving: the bot turns it into a rule proposal, "Do not report in shop/pricing.py: <finding> (reason: …)". See Learning from corrections.

fix ​

Switch PR fix on first

A fix run uses the shipped workflow PR fix, which is off on a fresh installation. A platform admin switches it on in Agents › Workflows, column On. While it is off, @octryx fix and @octryx write tests fail, even with Fix runs on, and the bot answers in the thread: "Octryx could not start the run: No published workflow 'pr-fix'."

A fix run runs on the commenter's own machine and subscription, at their cost and with their default coding engine. It needs:

  • the workflow PR fix switched on (see above);
  • Fix runs switched on for the repository (see Settings);
  • an open pull request that is not from a fork;
  • a source branch that is neither the target nor a protected branch.

Only one fix run per pull request runs at a time. It goes through the same independent review and pushes a new commit; it never force-pushes. Naming an engine in the command (@octryx fix codex) is not supported yet: the bot notes it and uses your default.

When commands arrive ​

With a webhook, at once. With Hourly sync only, the bot reads new comments every 2 minutes. With On every push (webhook) only, commands arrive only through the webhook.
