Python · story · Msplitbill: optional tip in percent
  • As a user I can add a tip in percent before the bill is split.
  • python3 -m splitbill 10.00 3 --tip 15 splits 11.50; the tip is added to the total and rounded half up to whole cents.
  • The tip is a whole number from 0 to 100; anything else prints an error and exits with code 2.
  • Without --tip the output is unchanged.
  • Unit tests for the tip and its validation; the CLI test covers one tip case. README and CHANGELOG updated. The leftover-cent rule stays.

Reproduce a round

  1. 01Get the casesoctryx-ai/octryx-bench holds the apps and every case brief, each on its own base branch, pinned to a commit. Clone it and check out the base of the case.git clone https://github.com/octryx-ai/octryx-bench.git cd octryx-bench git checkout base/python-bug-env
  2. 02Same machine, same modelClaude Code with Sonnet 5.5 on a Claude subscription. We run all six cases at once on one Mac, with no human step and a 45-minute limit per case.
  3. 03Octryx AICreate a work item with the brief, pick the workflow named in the case, start the run, and wait for the pull request.
  4. 04Claude Code aloneIn a clean clone of the same base commit, at the same time, run the line below. Its JSON output holds the token counts.claude -p "<brief>" --model claude-sonnet-5-5 --output-format json
  5. 05CompareTime to a pull request, tokens (input, output, cache), and what came out: tests, a review, a pull request. Run it more than once; the same story with Claude Code alone took between 9.5 and 23 minutes within one hour.

The setup

Two Workspaces, one per engine

“Coffee Bench Claude” runs Claude Code with Sonnet 5.5. “Coffee Bench Codex” is set up to run Codex with gpt-6.1-sol; Codex support is experimental. Each Workspace has its own rules, knowledge, memory and cost record, so nothing leaks from one to the other.

The same idea, the same tools

Both start from the same idea for a coffee web app. Both use the same Jira project, the same Confluence space and the same team conventions.

One repository, two folders

The code lives in one private repository with a folder per engine. Each Workspace indexes only its own folder.

Tested like a real app

Playwright runs as the system test in the pipeline. The reviewer is a separate session with no access to the author’s session.
