THE PROBLEM

Coding agents make each of us faster. But each person works alone with their agent: their own rules file, their own prompts, their own lessons. A fix one developer teaches their agent on Monday, the next developer teaches theirs again on Tuesday.

THE IDEA

Put a layer above the agents that the whole team shares: one process, one set of rules, one memory and a record of every run. What one person teaches, every teammate and every agent can reuse.

WHY IT MATTERS

Time is the most valuable resource.

AI should give us time back, not just more output. When knowledge is shared, mistakes aren’t repeated and results can be trusted, and people gain time for what matters. That is what Octryx is about.

THE STORY

Not a better agent. A better system around agents.

I built Octryx AI with coding agents myself. They made me fast, but files grew too large, old code piled up, tests got fitted to one scenario, and I started to lose the overview. The problem isn't the agents. It's that we use them alone.

So Octryx AI puts a team around them: a shared process, shared rules and shared knowledge. What one of us knows should be what the team knows.

Rules in one place, not in markdown files.

This is the main difference to a coding agent on its own.

A CODING AGENT ON ITS OWN
  • Rules usually live in markdown files in each repository (CLAUDE.md, AGENTS.md) or on one person’s machine.
  • Every repository keeps its own copy, and the copies drift apart.
  • Git records who changed such a file, but nothing ties a run to the rule version its agent actually read, and nothing keeps the copies of many repositories in line.
WITH OCTRYX AI
  • Code style, team rules and agent instructions live in the platform: set once for the installation, a Workspace or a repository, and governed in one place instead of per repository.
  • Versioned and audited; a change is visible, and a run records which version it used.
  • Every agent gets them at the start of a run, on any developer’s machine.

WHY OCTRYX AI

Proof, not promises.

  1. 01 Tested before it is offered The pipeline runs the tests your repository declares, on the server or the developer’s machine, and keeps per-test results and screenshots for the reviewer. In real runs
  2. 02 Independent review A separate model in its own session, with no access to the author’s session, reviews only what the server read itself: the diff, confirmed tests and screenshots. In real runs
  3. 03 Ask once, then work One question round for the whole epic, then stories in Jira in build order. The coding agent builds them; the platform adds branch, pipeline, review and pull requests. People merge — Octryx AI never does. In real runs
  4. 04 Your models, your infrastructure Developer machines with their own subscription, or company models through your gateway. Self-hosted, Apache 2.0. In real runs
  5. 05 A record of every run Each AI commit names its model and run; every run has a full event trail and its token usage. Built
Where Claude Code alone is better today For one developer on one quick task it needs no setup, and in our own tests it produced the nicer UI. Octryx AI adds tests, an independent review, a pull request and a record. On Flutter, the build and the browser test take most of the time. A comparison in tokens against Claude Code on its own is being measured. Results. Claude Code is a mature product; Octryx AI is an alpha. Use Octryx AI when a team needs a shared process, independent review and a record — not to go faster alone.

RUN IT YOURSELF

Start on one machine. No cloud lock-in.

Octryx AI needs Postgres, S3-compatible object storage and a model endpoint — nothing vendor-specific. The coding agents run on your developers' machines; each run can get its own short-lived sandbox container.

One machine with DockerBuilt
Docker Compose brings up Octryx AI with Postgres, object storage and migrations on a single host. Enter your model access in .env; secrets are generated for you. git clone https://github.com/octryx-ai/octryx.git cd octryx cp .env.example .env # fill in one model block docker compose up -d --build # with the demo Workspace: docker compose -f docker-compose.yml -f docker-compose.demo.yml up -d --build
